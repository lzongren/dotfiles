# Return: design for the first release

This is the engineering design for the workflow in [PRFAQ 0.8](PRFAQ-v0.8.en.md) question 14, built into the production `web/` dashboard for the Claude Code path. It covers stages 1a to 1d of question 24. The prototype in `prototypes/devbox-attention` remains a separate fictional demonstration.

The decisions fixed before this design:

- Recovery shows records only. No model summarizes, infers, or ranks anything Devbox displays.
- Investigation runs in a read-only copy of the conversation that Claude Code itself restricts.
- Repair goes back to the original session, and only when the user submits it.

## What the user gets

The flow follows the prototype in `prototypes/devbox-attention`, step for step: a home list of work, one work item, a draft or a question, then a receipt. Every line it shows is quoted, counted or matched from records, or a recorded number shown in seconds. Nothing is summarized by a model.

```
Home                                       Work page
┌ Pick up where you left off ──────────┐   ┌ Work ─────┬ ← Overview ──────────────────────────────────────┐
│ Needs you 2                          │   │ Needs you │ Fix API retry                                    │
│ ✕ Fix API retry  [Check failed]      │   │ ▌✕ Fix API│ PR #184 · 3 sessions · last visit 2d ago         │
│   Since you left  “…” failed · 12.6 s│──►│   ! Search│ [Changes & next step] [Result & acceptance]      │
│                   ● agent suggested …│   │           │ Check “keeps total deadline” failed [Hand back →]│
│                   · your rule: …     │   │           │ 12.6 s, limit 10 s         Opens a draft only    │
│   You changed     3 → 2 attempts …   │   │           │ ▸ Show the failed check     Ask first (read-only)│
│   you left 2d · idle 15m · PR #184   │   │           │ ┌ Where you left off ─────────────────────────┐  │
│   ▸ Goal and earlier decisions       │   │           │ │ Stopped at     Plan set: …                  │  │
│            [Review the failed check] │   │           │ │ Since you left “Budget decrement …” fix·17h │  │
│ ! Search evaluation  [Question]      │   │           │ │                “Two review findings …” rev… │  │
│   Last message    Should I compare … │   │           │ │                “… still fails” Then sug… ↓  │  │
│              [Answer the question]   │   │           │ │ What holds     at most 2 attempts (changed) │  │
│ › Nothing else needs you · Show all  │   │           │ │                Keep the 10 s … (failing ch) │  │
└──────────────────────────────────────┘   │           │ │                Don't raise … (agent named)  │  │
                                           │           │ └─────────────────────────────────────────────┘  │
                                           └───────────┴──────────────────────────────────────────────────┘
```

- **Layout.** The top bar holds search, which matches a session by name or title and opens it the way All sessions does, or starts Claude in a new folder of that name under the first sync root, and **New session**, which opens the new-session page. The overview and the work pages leave out the session sidebar; it comes back with a terminal tab. Each screen has one primary action, filled in the accent color. Status colors mean one thing each: red for a failed check or an error, amber for waiting on you (on All sessions a question takes the accent color, as in the prototype), a dot for new, a spinner for waiting on the agent. A changed limit, the current step and the open work are marked in neutral tones; a chosen option takes the accent border and fill. Disclosures and links are quiet grey text, cards are plain fills with a hairline, times are relative with the exact time on hover, and each is shown once.
- **Home.** "Pick up where you left off" holds the work around each Claude Code session that needs you, changed since you looked, or waits on a repair you sent. Each row shows the status (a red badge with a ring for a failed check, so it outranks amber), then labeled lines in one column: what came since you left — a failed check by name with its age and the value it measured, in seconds ("Check “keeps total deadline” failed 10m ago · 12.6 s, limit 10 s · may have passed since", since only failures are recorded), when its record has one and the agent is not waiting on you, or else what the agent said (its last message, when it waits on you) — with any agent suggestion under it ("The agent suggested “…” · your rule: “Don't raise it to 30 seconds”", by the same match, or "not set by you"), your rules (the one that matches a failed check when no value is shown, and the decision behind your setup, under one label, leaving out a rule a suggestion line already quotes) or your recorded reason, the last explicit change, the branch and pull request, the sessions in the work by name with what groups them ("3 sessions in PR #184: fix, review, tests", the PR as its link, "in PR #184 or its branch" when a member joined by branch; the facts line starts "last visit 3d ago", or "you looked 2m ago · visit before ended 3d ago" while this visit lasts, so it agrees with the work page's "Your last visit here ended", and "a read-only copy is answering" while a question runs), and one action: "Review the failed check", "See what changed", "Answer the question", "Continue the unsent draft", "Review the reply" or "See the handoff receipt". A work shows once, under its first session, except that a member keeps its own row when its lane is Needs you or it has its own draft, repair or question, because those belong to that session. Hand back from a reply opens a follow-up to the sent draft.
- **Work page.** A rail lists the same work, by section, each with its status only (and its session count once its brief is read); the work you are on stays in its group, marked current and showing the page's live status, so the rail counts what Now counts; when the list no longer holds it (accepted, say), it sits under "Open now"; with the page open, Devbox reads each listed work's brief it doesn't have yet (so a reload onto a work page keeps a failed check under Needs you) and rereads none, while the open work's brief follows the work page's own reads (so accepting or sending moves it in the rail at once); the rail's "N other sessions" is the same count as Now's, leaving out the open work's sessions as the work page last read them; switching through it saves the draft and records the visit, like going back. A work with no records, repairs or questions yet (a session just started) says "Nothing recorded yet", with your goal if you gave one and that the page fills in as the session records; its one button is **Open {session}'s terminal**, with no brief, no repair and no last visit. Otherwise the page opens on **Changes & next step**: any value still undecided, the brief, then what needs you now with its evidence. A failed check is named from its record with its age ("Check “keeps total deadline” failed 19m ago"), with the value it measured under it, in seconds ("12.6 s, limit 10 s", read from "Expected ≤ 10000ms · Received 12641ms", in tenths, or finer until the value and the bound differ: "10.04 s, limit 10 s"; a record in another shape shows its next line as written) an agent suggestion made since you left (or on a first visit) that names the amount of one of your rules under that, once, beside the rule — "The agent suggested “raising the deadline to 30 seconds” 16m ago · your rule: “Don't raise it to 30 seconds”". The match is on the value the suggestion sets ("from 10 s to 30 s" sets 30 s), with ms, seconds, minutes and hours compared by value however they are written and counts by their noun ("5 tries" is 5 attempts, and a bare number counts when the setting comes before it with a word like to, at, above or most in between, "never raise retries to 5", so "request 5" is not a count); when two rules name it, the one whose clause names the setting wins, and a clause that names a different setting ("the deadline", for a suggestion about the backoff, or any setting for one that names none) is not paired; every clause that holds the amount is tried; ranges count both ends ("10-20 s"); and the quote is the clause of the rule that holds the amount, split as in What holds (at a comma, semicolon or colon and a space, or a spaced dash, except a hyphen or en dash before a digit, so "10 - 30 s" and "3 – 5 attempts" stay whole). It never says whether the two agree: you read the rule in its own words. The home row and the work page use the same match, and that rule carries "named in an agent suggestion" in What holds — and the full record behind one quiet line that says only tool errors are recorded, so it may have passed since. Without a failed check, a fixed heading names the state and the agent's last message is quoted under it. Beside them sits the one filled button, **Hand back to the agent to repair**, with **Ask first (read-only)** as a quiet link under it; while a reply waits for review it is **Review the reply**, which opens Result & acceptance, and while a repair is out, **See the handoff receipt**. When the agent waits on you in its terminal (a question or a permission prompt), the filled button is **Answer in {session}'s terminal**, which opens its tab, because Devbox doesn't type into a waiting prompt; the repair is second, as "Draft the next step for after you answer". The brief has two columns, under a line with when you left and now: on the left Asked for (the session's first request, quoted), You last said (the sentences of your newest message in this session that What holds doesn't already quote, with "after your last visit here" when it is newer than your last visit), Why, Stopped at and Since you left; on the right What holds. Stopped at, Since you left (the last three agent messages in the work, oldest first, one row each, quoted without the sentences that hold a suggestion and followed in grey by the session and age, "“Budget decrement done. Running the boundary tests.” fix · 17h ago"; a suggestion that is not stated beside the next step sits in the row of its message, "Then suggested “…” · not set by you" (on Result & acceptance also "· your rule: …"); then a count of what the rows leave out (not counting the message You last said quotes; after a repair goes out, that row is "You sent “{its main line}”"), "Not shown: 1 of yours", a button that lists those records in place (and reads "Shown below: 1 of yours · hide" while they are), or, when no message is left to quote, a count of what the records hold since then: "3 agent messages, 1 of yours, 1 failed check, 1 shell line"; on Result & acceptance, which has no next step above it, a suggestion that names a rule's amount is stated in this row instead), Why (only when no rule or changed limit below already carries it), and What holds, which lists the same limits and rules as the draft, each rule with the rest of its sentence in small type, or its reason, or "no reason recorded", then who set it and when ("you, Oct 18, 09:36"); an unchanged limit shows the same with its reason. The rule that shares two words in a row with the check's first line is tagged with the check's name ("failing check"), in the red of the failed check above. A changed limit carries a quiet "changed 17h ago" tag, its old value and its reason. The title line names where repairs go and when your last visit here ended ("Your last visit here ended · Oct 15, 18:24, 2d ago", or, once you have looked within this visit, "You looked here 2m ago, this visit · the visit before ended …"; the brief's own line says "your last visit ended Oct 15, 18:24 · now …"), on every step, so it reads true next to what you did in this visit; that can be older than a message you typed in the session itself. While a question is open, the question opens right under the next step, and the brief under it keeps Stopped at and Since you left in view and folds only What holds ("1 limit, 3 rules"), and the question's Send is the one filled button. A line under the hand-back says it only opens a draft. **Result & acceptance** lists everything the repair sent you'd check the reply against: each line you asked (the request part of the sent message, leaving out the lines every draft carries and lines kept as an earlier comparison, with each item of the "Report back:" line on its own, and each sentence of a longer line on its own, so a reply that did one part isn't counted against the rest), then each other session's message you attached ("review: “…”"). The head says "Devbox doesn't check that the reply did these; it flags what the reply doesn't seem to mention". A line no reply sentence shares two of its words with (or the one, for a line with one word) is flagged, counted among what it may have missed and put in the follow-up. When it asks for several things joined by "and", the row names the parts no reply sentence covers ("The reply doesn't seem to mention “…”"), a hint that never changes what is flagged, or says "The reply may cover this only in part" when every part has a sentence; otherwise, when a reply sentence shares two of its words counting those your quoted rules and failures already use, and at least one of them is the line's own, it reads "The reply may cover this only in part · nearest in the reply: “…”" (that sentence may be quoted for other lines too), and else "The reply doesn't seem to mention this." Named parts are followed by " · nearest in the reply: “…”" when such a sentence exists (a line or question part naming a commit id the reply never repeats is flagged too, so an answer about another commit doesn't pass on shared words); any other line reads "Not checked", with the reply sentence that shares the most of its words beside it for comparison ("Not checked · nearest in the reply: “…”"), or "Not checked · read the reply for this." when none shares any, so a pairing never reads as coverage. A report-back item is checked for its kind of content instead: what you changed by a word like changed, fixed or added; the tests by "test"; their output by pass, fail or a time; what is unresolved by words like unresolved, still failing or nothing left. The messages you attached sit apart, under "Evidence you attached", read a part at a time (split like a question); a part is named only when the reply doesn't seem to mention it and none of your own flagged lines already covers it. Words are compared by stem; never, not, no, nothing, none, neither, nor, without and the n't forms count as one word, so "Never merge the PR" and "Nothing merged" share two; a shared number counts as two; the reply is split at each . ! ? or ; and a space. The words of the limits, rules and failure the repair quoted don't count, since a reply restates them anyway: "Respect the remaining budget within the 10 second total deadline" isn't mentioned by "I kept the 10 second deadline", unless fewer than two of the line's own words are left, when all its words count. On an unflagged line, each reply sentence is quoted as nearest for one line only, the one it shares the most with. An attached part your own flagged line already asks reads "The reply doesn't seem to mention “…” either; it's flagged above, in what you asked." A follow-up's opening line isn't one of the lines you asked, and the follow-up lists the flagged lines without the report-back items, which its Report back line asks again. "The reply says nothing was changed" shows when it says so. While anything is flagged, the filled button is "Draft a follow-up for what it may have missed", which starts a follow-up ("The reply to r-1 doesn't seem to cover these. Do each, or say why not:", the flagged lines, and the Report back line) and opens it, and Accept is the quiet "Accept anyway", sized to its label, with "The 3 things it may have missed stay listed on Now after you accept." beside it; the accepted card on Now lists all of them under "May have missed" (the summary's `missed`). A work whose newest repair you accepted opens on this step, unless a newer draft is unsent. Once you accept, the step's heading says "You accepted this result · merge is still yours", with "You accepted it 1m ago. That records that you read the reply; it doesn't merge, push or close anything." under it. A disabled button has a dashed border, so it reads differently from a quiet one. The result's list holds each limit, each of your rules ("not checked by Devbox", after "failing check · " for the rule the failing check names, or "failed before the repair · " once a repair went out after it), and merging. The step's lead says Devbox doesn't run checks or read the reply for meaning, that each limit shows whether it changed after the repair was sent, and that a line you asked for is flagged when the reply doesn't seem to mention it; the rest is yours to read. The list's two columns line up. A receipt for an accepted repair reads "Replied · you accepted it 3m ago". An earlier round a later reply followed reads "Replied · r-2 followed it", with its own reply under "Show its reply" instead of a link to the newer one. Once the newest repair is accepted and nothing failed since or waits on you, the Changes step says "You accepted the result · merge is still yours", its filled button is Back to Now, and Hand back becomes the quiet "Hand back another repair". The reply comes first, right under the step's lead, then what you asked, the evidence you attached, the limits and rules, Accept, and any question panel; the page lands on the step's heading, and changing steps scrolls back up to the steps. The latest reply (flagged when it doesn't start with the `[devbox result {id}]` the repair asked for, or repeats the previous round's reply word for word), what it was made under, "Merging, pushing or deploying: not done by Devbox; the repair told the agent not to, and Devbox can't see whether it did" ("Devbox never does it" before any reply), the last recorded failure ("before this repair. Devbox records only failures, so whether the checks pass now is the reply's word, not a check", or that a check failed after it was sent), and Accept as the one filled button; the Changes step keeps the same last-failure note once a repair has gone out, replied or not, and What holds tags the rule that matches it "failed before the repair". The receipt says "Accepted" once you accept, and every receipt restates the scope: "Asked for edits in {folder} and the tests needed to check them · no merge, push or deploy. Requested in the message, not enforced by Devbox." The draft's "Asks for" line says the same before sending. A draft can be discarded, after an inline confirm. Once a reply came back, Ask first starts from a question about the reply instead of the old failure. Suggestions made before the newest repair that went out are no longer listed as news. Opening a work with a new reply scrolls to the result step's heading, and one with a new answer to the answer. While the question panel is open, the draft's action bar stops sticking, so only one Send stays in view. The rail's "Open now" status says "Check failed" when the brief shows one. Opening the app on a work's address still reads the home list's briefs once, so the rail and All sessions know the groups. Times in the brief are local; packets keep UTC. **Handoff draft** becomes **Handoff receipt** once the draft goes out.
- **Draft.** Handing back fills in a draft from the records: the failing check, what to treat as evidence, and what to report. The draft step checks it against the basis you saved, names the target conversation, lists under "What holds · added to the message" the limits, the rules (this session's unless unticked, behind one quiet line), what the other sessions' agents said since you left (every message the draft keeps, however old, and the last three since you left, each quoted with session and age and its own tick, at most 20 ticked; those there when the draft starts are ticked and later ones listed unticked; a ticked message that has left the records is named as not sent, still counts toward the 20 so it is kept if it comes back, and can be forgotten from that line; the draft keeps the ids it ticks and the send quotes exactly those, in time order, so the row, the preview and the send match and nothing is added or dropped unseen; a send whose packet would differ from the preview is refused and the view reloads) and what the repair allows, and offers Send, Ask first, and "Back (keeps the draft)" in a bar that stays in view. The receipt offers the next work that needs you.
- **Questions.** "Ask first (read-only)" opens **Ask (read-only)** with a filled-in question. One line says it isn't sent yet, that a read-only copy answers, that the session never sees it, and the cost ("costs up to about $1"); the draft won't go with it. Each question keeps its own receipt; a running one names the copy it runs in ("running in a read-only copy of fix…"). Each answer says it is not verified: a read-only copy wrote it and nothing ran to check it. Older answers fold under their questions. An unsent question stays in the tab across a reload; the filled-in question counts only once you change it. The filled-in question fits what is open: the reply once one came back, the failed check when there is one, what the agent waits for you to decide when it waits on you, or else what changed since you left. Each part of the question (split at ?, ., ; and "and", leaving out how to answer: "Don't …", "Separate facts …", "say what is unknown", and a leading "Using the recorded messages,") that no sentence of the answer shares two words with is named, by the same rule as a reply: "The answer doesn't seem to cover “…”." with "Ask about that part", which opens a question filled with those parts. One-word parts aren't named. The answer's status is then "answered · may miss part of your question", or, when the question's first part is the one not covered, "answered · may not address your question" with "The answer may not address your question; it shares too few of its words.", else "answered". A part naming a commit id the answer never repeats isn't covered. Searching saved records marks a limit you later replaced ("replaced by at most 2 attempts").
- **Receipt.** After Send, a banner shows the repair's state, scrolled into view once it appears, the home row moves to "Waiting on the agent", and the step shows the status, the exact text sent, and Back to the overview.

## Screens around the work

The prototype's other screens, in the same records-only terms:

```
top bar:  devbox  [Now] [All sessions 32] [Artifacts]        search · New session · theme
             │          │                     │
             │          │                     └ every PR and file the records name; a row opens its work
             │          └ one searchable list; a row opens its work, else its terminal
             └ home ── work page:  [Changes & decisions] [fix ⌁] [review ⌁] [+ New session]
                                        │                   │              │
                                        steps as above      live terminal  type · name · folder
                                                            under "Keeps   · which work it joins
                                                            holding …"
```

- **Navigation.** The top bar adds Now, All sessions (with the count) and Artifacts. Now is the home list, or the work page you have open. Choosing one leaves any terminal tab. All sessions, Artifacts and New session start with "← Back to Now"; a work page opened from All sessions or Artifacts starts with "← Back to All sessions" (or Artifacts) and returns there, while Now in the top bar always goes home. A terminal tab opened outside a work shows the same work rail as the work page in the sidebar, with only the sessions outside those works listed under it (and no "Nothing needs you" there, since the rail says what needs you). The tab strip shows only while a terminal tab is open; its first tab is named after the page it returns to, with the count of sessions that need you as the home list counts them. On the pages themselves there is no tab strip, as in the prototype; an open terminal stays connected and opens again from All sessions, search or its row.
- **Home.** Above the list: today's date and time zone, what Devbox is reading ("Reading dev · 32 sessions", or "Not reaching dev"), and one count line, "2 need you · 1 new · 1 waiting on the agent". With nothing under Needs you or New it says "You can leave now", and what still waits on an agent (and "What you haven't sent is saved." when something is under Not sent yet), or, when a session outside the list needs you (a Codex or shell session), "Nothing listed here needs you, but other sessions do". The other sessions fold into one quiet row, "26 other sessions · 1 needs you · View all", that opens All sessions. The other-sessions row doesn't count a session of a work you went back from this visit. The works you went back from this visit stay under "Seen this visit", with their return note (open when one has a note, such as an accepted result), so you can reopen one; the list lasts for the tab's life, across reloads. A work you looked at within the visit gap keeps being read, so a failed check you didn't act on stays under Needs you. Choosing Now, or Back to Now from All sessions, Artifacts or the new-session page, goes home, leaving an open work the way Back does; from a terminal tab too, Now in the top bar goes home; the first tab returns to the page under it. The address keeps where you are, replaced in place rather than added to history: `#w={session}` for a work, `#s={session}` for a terminal tab, `#sessions`, `#artifacts` or `#new`, so a reload comes back to it once the sessions are read (the `#t=` token fragment is read and dropped before that). A row's meta line says "waiting on you" or "agent idle" and for how long. A reply on a row reads "The reply says, not checked: “…”", the caveat first so a clipped line keeps it, before and after you accept it. The session lanes, cards and details pane are gone.
- **New session.** Other sessions' messages are offered unticked ("Tick one to attach it · quoted as written and not checked"), so nothing unverified goes out unless you choose it. The goal field is labeled "Your goal for it (optional, for you only)": it names the session (dropping a trailing "the", "for" and the like) and shows beside it, and isn't sent to the agent. From the top bar, the context says it isn't tied to any work. In a work's member list, the main session reads "the work's main session; repairs and questions go here".
- **All sessions.** Every session, one row each: its agent, title, host · path (and "Codex: no brief or repair yet" for a Codex session, since only Claude Code records are read), the work it belongs to (the home row's title, or the title from any brief read this visit, so a work that left the home list keeps its sessions) or "Nothing new", and its state, every return note first, joined ("Waiting on the agent · Question running"), then "Check failed" for the session whose home row says so, and "Idle" for a session Devbox reads no agent state for ("Idle, its turn is done" for an agent between turns). Rows needing you come first (the main session of a work under Needs you counts, and its state takes the same color), then working, new, and the rest by activity. The search also matches the goal you started a session with. A search field filters by name, title, path and work, with the count of results. The count line says how to move: ↓ from the search box, then j and k between rows; Enter or a click opens the row's work: the home row whose work holds it, else the session's own page, at its terminal tab when Devbox reads no agent state for it.
- **Artifacts.** Every pull request or review link the records name, newest first, then the files the agents wrote. Each row names the sessions it came from, first to last, each with what it did and when it first named it ("fix created 15m ago, review reviewed 5m ago"), as the artifact lists elsewhere date it (which read as a phrase: "PR #184 reviewed by review 1d ago · named 3 times", "retry-plan.md in docs/ created by fix 2d ago"), and opens the work of the newest one still running on its Changes & decisions tab; a quiet link opens the pull request in a new tab, or the file in the preview.
- **Work tabs.** Under the title, the work page has tabs: Changes & decisions (the steps above), one per session in the work, and + New session. The title line's ⓘ opens a popover on why the sessions are together, with Show separately, and the sessions you showed separately (with Undo) and the ones that only look related under their own "Kept separate" heading; for a work of one session it's titled "Why it's on its own" and adds that no other session shares a pull request or branch with it; Escape or a click elsewhere closes it. The session you showed separately says so on its own page, "You showed tests separately from the work on branch fix/retry-budget.", with Undo, which takes you back to that work's page when the home list holds it, so the separated session never becomes the page's main session. The title line counts them ("2 sessions grouped automatically · 1 you showed separately"). A session tab's name is cut with an ellipsis past 24 characters, the full name on hover. Showing one separately also says so under the title, with Undo (undoing says "{name} is back in this work."), and the rail, home rows and All sessions take the work as the page read it, at once. Under the steps, one fold, "Full results, history and linked sessions", holds three tabs: Results & evidence (the last failed check, the work's links and files), Linked sessions, and History (where you stopped, each record a later limit replaced marked "replaced by …", since you left, how Devbox reads constraints). The change log under the next step names the session of every record ("agent in fix", "you in fix"), and gives the failed check shown above one line, "· in full above". A session tab shows its live terminal under a bar that quotes what holds ("Keeps holding while you continue: at most 2 attempts; Never merge without me"), and says that what you type there goes straight to the session unchecked; a repair from the draft is checked (said only where a repair can go). When that session's agent waits on you, a line above names what it asks ("ranking is waiting for you (question): “…”. Type your answer at its prompt below; Devbox doesn't type into a waiting prompt."). Beside the terminal, the same three tabs, on screens wide enough to keep the terminal at 80 columns. The last three terminals you opened stay connected while you switch tabs, and close when you leave the work. "Open the full-screen terminal" moves the terminal to a terminal tab, so no session has two of them here. A terminal tab of a session in a work read this visit keeps a strip over the terminal: "In {work} · keeps holding: …", that typing there is unchecked, and Back to the work. While a work page is open, the first tab of the tab row is named after the work instead of Now. Opening another work from All sessions or Artifacts leaves this one the way Back does: the draft is saved first, or the page says why it stayed. Opening a session that belongs to a work opens that work on the session's tab. The tab quotes the goal you started the session with, if any ("Your goal when you started tests: “…”"). A switch asked of the work page before it opened (a stale one, after you went to another work) is ignored, so the rail and Now open the work you choose. The rail is headed "Grouped by shared pull request or branch", shows each work's session count and status, and ends with the other sessions' count and View all.
- **New session in a work.** Titled "Add a session to {work}". Shell, Claude or Codex; an optional goal, whose words become the session's name (cut at a word to 32 characters) (else the folder's session name and the agent, "fix-claude"), made unique, and which the server keeps beside a session it created (`goal` in the session's state, never sent to the agent; a created session starts with none of the state an old session of its name left): All sessions shows "Your goal: …" under the row and the why panel "Your goal when you started it: “…”" under the member; the machine; and the folder of a session in the work. It says whether the new session joins this work, by the grouping rule: "Joins “Fix API retry”: same branch fix/retry-budget in api", or "Opens on its own page: fix's folder is on main, so it won't group by itself". The server maps the session's folder to its local mirror, the synced root itself included, refuses a folder whose real path leaves the root, and starts `devbox --detach [--fresh --cc|--codex] <name> <folder>` there. A Claude or Codex session starts a new conversation (`--fresh` runs `claude` or `codex`, not `--continue` or `resume --last`), so it can't write into the conversation a repair goes to. That conversation is then the folder's newest: if the original session restarts later, `devbox --cc` there continues it, and the form says so. Nothing is typed into the new session; it opens in its own tab. Beside the form, the current work and the session that keeps running.
- **New session from the top bar.** The same form on its own page, with a sync root for the folder: the session starts in a new folder named after it, never one that already exists or a running session's name. It says it opens on its own page until it shares a pull request or branch. Every session, Claude, Codex or shell, then opens on a page of its own, at its terminal tab, the way a session opened from the sidebar, All sessions or search does; only "Open the full-screen terminal" and "Open beside terminal" use the tab strip, whose home tab's counts carry their meaning on hover. On Now, "Answer the question" opens the work on the waiting session's terminal tab, where the answer goes.

## Stage 1a: records and provenance

### Records

The probe's return mode takes one session name. It finds the session's Claude Code pane, the pane's entry in `~/.claude/sessions/*.json`, and that entry's transcript. It reads the transcript from the start, cached by inode and size, and emits:

| Record | Taken from | Author |
| --- | --- | --- |
| decision | every human prompt, using the existing `human_prompt` rules | you |
| agent | the last text block of each agent turn | agent |
| failure | tool results marked as errors, first 600 characters | tool |
| shell | the last 40 lines of a grouped shell pane | shell `<session>` |

Each record has the transcript uuid as its id, its timestamp, and its turn number. The probe also returns the session id, cwd, git branch, repository top level, pull request URLs, the registry status, and a version: `inode:size:last uuid`.

The probe never runs a model and never writes. Caps: 200 decisions, 60 agent turns, 30 failures, 4 KB per record. Older records are counted and marked as not loaded rather than dropped silently.

### Constraints

`constraints(records)` splits each decision into sentences and matches these rules. They are disclosed in the UI under "How Devbox reads constraints":

- A limit: `at most`, `no more than`, `max`, `maximum`, `up to`, `limit to`, `cap at`, `at least`, `minimum`, or `exactly`, followed by a number and a unit. The units are attempts, retries, tries, times, ms, seconds, minutes, hours, percent, requests, workers, threads, files, lines, MB, and GB.
- A prohibition or requirement: a sentence starting with or containing `never`, `do not`, `don't`, `must not`, `only`, `must`, `always`, or a held-constant phrase (`on the same`, `with the same`, `use the same`, `keep the same`, `against the same`: "Evaluate the new ranker on the same data version and random seed"). These are shown, but only limits can conflict, because Devbox doesn't understand their meaning.

The **subject** of a limit is its unit, normalized to singular, plus the noun before it when there is one ("total timeout 10 seconds" gives `timeout/second`). Retries and attempts are different subjects: two retries are three attempts. A duration's subject is the timing noun a cap names ("cap the backoff at 2 s"), else the first of timeout, deadline, backoff, delay, interval, budget, ttl, wait, latency and sleep named in its sentence ("times out" names the timeout), else plain duration. Two timing settings in one sentence share that word: "keep the backoff at most 2 s and the timeout at most 10 s" reads as two timeouts and shows as undecided, so write them as two sentences.

A later user limit **replaces** an earlier one with the same subject only when its sentence contains an explicit cue: `instead of`, `replace`, `rather than`, `no longer`, `from N to M`, `change … to`, or `update … to`. Otherwise two different values are a **conflict**, shown with both sources, and nothing is effective until the user decides for this work. An agent's sentence never replaces a user's. Agent limits are listed as suggestions.

The **reason** is the clause after `because`, `so that`, or `due to` in the same sentence, or a next sentence that starts with `Because` or `The reason is`. `since` and `as` are left out because they usually mean time or comparison. Without a reason, the item says "No reason recorded".

### The brief

`briefOf(entries, constraints, session, leftAt)` picks lines from records; it never rewrites them:

| Line | Taken from |
| --- | --- |
| Left | the last Return visit, else when you last looked at the session in the overview |
| Why | the newest reason recorded with one of your limits or rules at or before you left; else, as written, the newest of your limits or rules in force from then (the longest when one message set several); else the newest reason at all |
| Stopped at | the agent's last message at or before you left |
| Updated | the newest limit that explicitly replaced another: old value → new value, with its time |
| Since you left | the session's latest agent message after you left, without the sentences that hold a flagged agent suggestion (the brief shows those apart) |
| Failing | the newest tool error in any session of the work after the newest repair that went out, whether or not you looked at it since |
| Agent suggestions | agent limits whose subject you didn't set, or set to another value. The brief says none of your messages sets it, not that you disagreed: you may have agreed in words Devbox doesn't read |
| Not recorded | limits in force with no recorded reason |

An agent suggestion also matches "raise", "increase", "lower", "reduce" or "set" followed by a subject, `to`, a number and a unit, so "I suggest raising the deadline to 30 seconds" counts. Only agent messages are read this way.

The headline over the next step is fixed text chosen by state: a failing check since you left, the agent waiting on you, a reply to review, the agent working, or a finished turn. The lead under it quotes the failure or the agent's last message.

`GET /api/return/brief?session=&left=` returns the work and the brief for one session, counted from the session's last Return visit, else from `left` (when you last looked at it in the overview). It reads the host like the Return view, under the same lock, and moves a sent repair on from what it read, so the overview learns of a reply without opening the work. A failure from before the newest repair that went out isn't the failing check any more. The overview asks for the rows it shows, once per change in the session's activity or in when you last looked at it, and after each visit to its work page, one at a time, and not while a work page is open, so a work page never waits behind a brief. A brief that fails is asked for again after a minute. Leaving a work page, by going back or through the rail, records the visit and counts the page's session as seen; the work's other sessions count as seen as they were when you opened the page, and the one you switch to stays unseen. Their briefs still count from their own last visit.

### Since you left

`lookedAt` is when the user last left this work's page, and `seenAt` is where the visit before this one ended, both stored server-side. A visit ends after 30 minutes without looking (`VISIT_GAP`): until then "Since you left", the brief and the home row keep counting from `seenAt`, so going back, reloading, or switching works doesn't move them; after it, the last look becomes where you left. "Since you left" lists records after it. Files, commits and pull requests stay on the session's card. On the first visit everything appears under "Where you stopped" and "Since you left" is empty. Tool errors are listed but tool calls that worked are not, so the list says a later attempt may have succeeded.

### Grouping

A work item groups sessions only by a stable identifier:

- the same pull request URL in the probe's artifacts, or
- the same repository top level and the same branch, when the branch isn't `main`, `master`, `develop`, or detached.

The same folder or a similar name never groups sessions. Each member shows why it is included. Sessions that only look related, on a branch of the same name in another repository or in a folder of the same name, are listed as not in this work, with that reason. A session in the same repository on the same default branch, and the home folder, aren't listed this way. **Show separately** records a separation for that work and that session, and it can be undone. A separation affects only reading: original records aren't touched.

## Stage 1b: the draft

A work item has one repair draft, stored server-side with:

- `text`
- `basis`: the effective constraints and their source record ids when it was last checked
- `corrections`: `{ id, line, before, after }` for each applied change
- `earlier`: the trimmed text of each line kept as an earlier comparison; every line with that text is kept
- `target`: session name, pane id, and session id when the draft was started. If the pane now runs a different conversation, the draft says so and sends nothing until the user picks the conversation running now. Once the draft has gone out, its repair keeps the conversation it went to, and the view stops asking.
- `quote`: which rules the repair quotes, by rule, under "Quoted with it, from your messages" in the draft step. A rule from the target session is quoted unless the user unticks it, so the draft never looks like it drops a rule the user set and a compacted conversation still gets it. Another session's rule is quoted only if ticked: it is often scoped to that session's task. A one-off rule such as "Don't edit anything yet" can contradict a repair; the packet tells the agent to stop and ask on a conflict. Devbox doesn't guess which rules still apply.
- `setAside`: rules the user set aside for this repair only. The packet lists them as set aside instead of quoting them as binding.
- `read`: amounts the user confirmed as written, by line text and amount
- `follows`: the send time of the repair this draft follows up, once a follow-up starts

Kept lines, set-asides made for a line, and confirms are tied to the line's text. `pruned()` drops any whose line is gone; the view runs it on every change and the server on every save, so a line typed back later never comes back already kept or confirmed. A follow-up on a draft that went out (Hand back, Write a follow-up, or the follow-up for what a reply missed) starts with no corrections, keeps, set-asides or confirms, since those were for the repair already sent, and records that repair's send time as `follows`, so opening the same follow-up again keeps what you chose in it. `shownAs(draft, version, repairs)` is the one test of whether the step shows a receipt or the open draft, used by the view, the step a work opens on and the Now summaries: the newest repair that went out with this text, unless it went out at or before `follows`. So a follow-up opens the same way after a reload or in another tab; trying the followed repair again, or any newer repair going out, shows the receipt; and a follow-up whose text goes back to an older sent repair stays open and says it was already sent. While a follow-up is open, the step reads Handoff draft and the hand-back button reads Continue the unsent draft, and discarding its text keeps `follows`, as does the draft Hand back starts after it. A retry is a new send, so a follow-up after it starts fresh too; while a retry is in flight (one host round trip) the draft reads as sent, and a refusal puts the earlier record back. Each repair keeps the keeps, set-asides and confirms it went out with (`checked`) until it is delivered or fails, and a held or unknown repair tried again is checked with those, whatever a follow-up changed since. Once a newer repair went out (`newerThan`), an older held or unknown one, which may have landed, is not tried again (`superseded`); its receipt drops Try again and Edit the draft to send it again, says the newest later one went out after it, and, while its session, pane and conversation are still there and it was not lost (`lostAt`), asks to clear the old paste from the prompt. A failed repair never went out, so it is not superseded; `retryBlock(repair, now)` is the one answer to whether a repair can be tried again, and why not: `not_retryable` (it went out and was seen), `superseded`, `lost`, `draft_changed` (not the draft's saved version), `already_sent` (a failed one whose text went out since), `basis_changed` (what holds changed after a held or unknown one went out), `no_registry` (no Claude Code conversation with a transcript is visible there, `conversationOf`), `no_target` (a failed one's draft names no conversation) or `other_conversation` (a different one runs there than the repair, or for a failed one the draft, names). The server checks the same conditions in its send order, recording a held or unknown repair's move as before, and a test pins that each code, when it is the only thing stopping a retry, is the code the server refuses with; when several apply, the server may name an earlier check of its own (changed evidence or a draft finding). A pane with no Claude Code at all is refused as `not_agent`, which `retryBlock` reads as `no_registry`. The server's own `no_registry` check leaves the record as it was; only a refusal from the host moves a repair to held. Try again is offered on a held or unknown receipt only, when `retryBlock` is empty and no save is pending. A failed repair has no Try again: it never went out, so Send on the draft step sends it again under the same id, rebuilt from the draft as it is now. Send picks the id after the draft is saved, so it reuses a failed repair only when the saved text is that repair's. A held or unknown receipt that can't be tried again says why in one line, adds to clear the old paste from the prompt when it may still be there (same session, pane and conversation, not lost), and to edit the draft to send it again when what holds or the conversation changed; while no conversation is visible it says Devbox can't try it again yet. A held one that can be tried again says to send it from the terminal or clear the prompt and try again. A failed receipt names only a history reason (the draft changed, or its text went out again); a conversation reason for it is the draft's own, shown by the draft step (choose the conversation running now). Otherwise it says sending this draft tries it again. A held draft's send line only says it was already sent and is held in the prompt, and that its receipt says what to do. A retry the host answers with failed, which it says only after seeing an empty prompt, marks a held repair failed, and from then on it is tried again like any failed one, from the draft as it is now; an unknown one keeps its earlier record. A failed repair never went out, so it does not supersede an older one. A draft save may be up to 1 MB; a larger one is refused as too large and stays unsaved in the view. Choices changed in two tabs on the same text are saved last one wins, since the version follows the text; the server checks the stored draft and the preview, so a tab still showing an older choice can't send it.

**Hand back to the agent to repair** starts an empty draft from `draftFor(brief, session)`:

```
Please continue in this conversation.

Decision: find and fix why the recorded failure quoted below fails, then rerun the checks that cover it.
Follow my decisions and the limits quoted below, not earlier agent suggestions.
Report back: what you changed, which tests you ran and their output, and what is still unresolved.
```

Without a failing check, the decision line asks the agent to pick up from its last message ("Decision: pick up from your last message and finish what it leaves open."), which it has in its own conversation. Neither line quotes a check name or an agent message, so the draft holds no tool or agent text, and every line is checked. The home row and the brief's "You sent" name the check, kept with the repair when it goes out ("You sent “Decision: find and fix why ‘keeps total deadline’ fails, …”"), or say "find and fix the recorded failure" when no repair kept one. The failed check itself is not in the editable text: the packet quotes the latest recorded failure under "What this is based on", so editing the draft can't drop the evidence. The draft names no limits itself, so it can't restate a stale one; the packet quotes what holds now. An existing draft is never replaced.

`draftIssues(text, effective)` finds each limit in the draft whose subject has a different effective value, written as a limit ("at most 3 attempts") or as a setting ("increase the number of attempts to 3", unless the line keeps it out first; a limit or setting within every limit held on that setting, "lower the timeout to 10 seconds" or "at most 10 seconds" under at most 30 seconds, is not an issue, while "lower the timeout to 5 seconds" under at least 10 seconds is). For each issue:

- **Change to N** rewrites only that number in that line and records a correction.
- **Keep as an earlier comparison** records the line's trimmed text, for any line that differs from a limit: Devbox doesn't guess whether a line describes the past, since every way of guessing let some instruction through. Keeping covers every limit finding on that line and on any line with the same text, now or later (rule, scope, loosened-limit and unchecked-amount checks still apply), Keep shows once per line, a kept line keeps its note even once it no longer differs, and the card says the whole line, and any line the same, then goes out marked as not a requirement and that the result doesn't check the reply against it. The sentence is sent with a note inline that it describes earlier behavior and is not a requirement. The check then says how many lines it kept that way, not a plain match, and each has Undo.

`draftRuleHits(text, effective, setAside)` finds, unless the line keeps it out first (don't, never, not, without, instead of), each line that:

- sets an amount ("raise", "increase", "lower", "reduce", "set", "bump", "extend", "change", "cut", "shorten" or "lengthen" the (total, overall, whole or maximum) setting to an amount, the same pattern as agent suggestions, with up to two words before the setting, "the overall request timeout") that one of your rules keeps out, by the same match as the suggestion line ("Don't raise it to 30 seconds");
- sets a setting that one of your rules fixes at another amount, a timeout and a deadline counting as one setting ("increase the total deadline to 15 seconds" against "Keep the 10 second total deadline and retry only idempotent requests"; a rule with a bound, "at most 2", allows what fits it);
- does what a rule says never to do, by its verb and object ("merge the PR" against "Never merge the PR without asking me"), unless the line asks you first. A rule whose clause names an amount is left to the amount checks.

Every rule is checked: setting one aside leaves the line flagged by any other rule it breaks. Each flagged line gets one card, quoting the line once, with each finding on it (a limit it differs from, a rule it breaks, a merge or set-aside it asks for, an amount Devbox can't check) and that finding's action. The heading counts the cards, adds the findings when a line has more than one, and the amounts Devbox can't check ("2 lines flagged · 1 amount Devbox can't check"). An amount you confirmed as written leaves its card and the count, and shows as a grey "Confirmed as written: line 2, “three attempts”." with Undo. A setting a held limit covers is a draft issue instead. Each hit quotes the line and the rule's clause and blocks Send until you edit the line or **make an exception for this line only** ("You kept line 3 against this rule. For this repair, that line wins over it; the rule still holds for the rest of the message and after it"); the server refuses with `rule_conflicts` on the same check. An exception is kept in `setAside` as the rule key and the line's text, so it covers that line as written and nothing else: the same rule still flags any other line, and editing the line ends the exception. The rule stays quoted as binding, and the packet adds "For this request only, I make an exception to my rule from {time}: "{sentence}", for this line only: "{line}". The rest of the rule still holds." (the precedence line then ends "except where I make an exception below"). A whole-rule key, from older drafts, still sets the rule aside as before. The heading adds "· N exceptions to your rules". Exceptions have Undo, and last for that repair only: a follow-up starts without the sent round's corrections and exceptions.

A line that asks for a merge, push or deploy (push in the git sense: "what pushes the total over the deadline" isn't one, nor is a "merge conflict"; a quoted command such as "git push" is; not kept out by "don't", "never", "without" and the like, not asking you first, whether or not it describes the past: "The old code pushed twice" blocks too, since no reading of history is safe enough for a block that can't be overridden; reword it) blocks Send whatever rules are set aside: "Line 2 asks for “Merge”. A repair never merges, pushes or deploys: the message tells the agent not to. Remove it; that step stays yours." A line that asks the agent to ignore, disregard, skip, bypass, override or disable your limits, rules, constraints, tests or checks ("Ignore the limits quoted below", "Skip the keeps total deadline test"), or to mark something as skipped, pending, todo or flaky, or to delete, remove or comment out an assertion, test or check, blocks Send the same way: "A repair can't set aside your limits, rules or checks this way. Remove it, or change the limit or rule itself." The server refuses both with `out_of_scope`.

`uncheckedAmounts(text, effective)` lists amounts written in words ("three attempts", "half a minute", "a third try"; an ordinal counts only after "a" or "an", so "skip the second attempt" is not an amount), and, while an attempt limit holds, counts of times or retries ("retry up to 3 times"), whose relation to attempts Devbox can't tell. A digit amount whose unit belongs to a held subject, or to one a rule names an amount for (a duration while a deadline holds or a rule names "the 10 second total deadline", say "Use 30000 ms as the total deadline budget"), but that Devbox doesn't read as a limit or a suggestion is listed too, unless it is the value that holds now or one a rule states (not one it keeps out): "fit 2 attempts" under at most 2 attempts, or "the 10 second total deadline" under that rule, is not listed. Overlapping finds count once, so "one more try" is one amount, not two. "Allow 3 attempts" and "permit only 2 retries" are read as limits. Spelled-out counts of requests, lines, files or items are not listed, and an amount on a line written as history ("The old code tried 3 attempts") is asked about like any other. A count of retries or times says it "may mean 3 or 4 attempts", unless both readings break the attempt limit ("allow 3 retries" under at most 2 attempts), which makes it a line that differs from the limit, with "Change only this to at most 2 attempts". "Try each request three times" reads as 3 attempts. A limit Devbox reads on a setting that holds no limit ("let the overall timeout go up to 30000 ms") is checked against the amounts your rules name, like a suggestion. While an attempt limit holds, relative wording ("once more", "one more try", "another attempt", "twice more") is listed too. A line that loosens a setting a limit or rule fixes, with no number ("Loosen the total deadline", "Add one more retry", "Give it another attempt"), is flagged: against a rule it is a rule hit with the exception choice; against a limit that holds it reads "Line 3 asks to add one more retry; at most 2 attempts holds now. Edit the line. To go past the limit, change the limit itself first.", blocks Send, and the server refuses it with `limit_pushes`. An amount a recorded failure measured (12.6 s, from "Received 12641ms") counts as known, so Devbox doesn't ask you to confirm its own number; a follow-up on a sent draft starts with no confirmations. Lines are numbered as the box shows them, blank lines included. "half a minute" and "half an hour" read as 30 seconds and 30 minutes, so "Raise the deadline to half a minute" meets "Don't raise it to 30 seconds". The heading counts findings beyond its flagged lines only when a line has more than an unchecked amount. A change's undo goes away once you edit that line again. A digit amount a replaced limit set says so: "Line 1 says “3 attempts”, the old limit: at most 3 attempts was replaced by at most 2 attempts." Each blocks Send until you rewrite it or choose "Confirm as written" (kept in the draft as `read`, and checked again by the server, which refuses with `unchecked_amounts`); the heading says "N amounts Devbox can't check" instead of a match, and each line says to write it like the limit that holds now, a time limit for a duration and the attempt limit for a count. Amounts written as number words (one to twenty, thirty to ninety) are read like digits wherever limits, suggestions and rule amounts are read, so "allow up to three attempts" is a limit and "bump the total budget to thirty seconds" meets the rule "Don't raise it to 30 seconds"; other wordings ("a few attempts", "half a minute") stay amounts Devbox can't check. A line that keeps out an amount a rule keeps out ("do not raise it to 30 seconds") restates the rule and isn't listed. Once you confirm amounts as written, the heading says so: "· 2 amounts you confirmed unchecked". The first reason Send is disabled shows beside it, in the action bar. A clean draft's heading, with no check mark, is "Nothing flagged in the limits Devbox checks · it checks limits like “at most 2 attempts”, amounts your rules name and “never” rules; read your other rules yourself".

Undo finds the corrected line by its text. If the line was edited afterward and no longer matches exactly once, undo refuses and says why instead of overwriting the edit; once no line of the draft shares two words with the corrected line, the note goes. The next correction or edit clears the old undo message.

When the user returns, `differences(basis, effective)` lists only constraints whose value, source, or replacement changed. An unchanged basis asks for nothing.

A draft is sent once. After a send that didn't fail, the same draft version can't be sent again. The version follows the trimmed text only: ticking a rule, checking changes or choosing the conversation keeps it, and only editing the text makes a new one. So a retry of a failed send still goes out after you choose the conversation running now. Send waits while the agent is busy or waiting on the user, and says so; the server still refuses on its own check. The view checks again at the slow pace (15 s) while it waits. If saving the latest edit fails or conflicts, nothing is sent, including a save still under way when Send is pressed.

**Discard this draft** asks once ("Discard the draft? Its text can't be brought back.") and saves it empty. Drafts save on each change, debounced 500 ms, and on leaving the view, with a version for conflicts like Notes. They survive a server restart and clearing the browser. They don't sync between laptops. If the last edit can't be saved, going back stays once and says so.

## Stage 1c: sending

### Repair to the original session

`POST /api/return/repair { session, requestId, preview, version }`, where the browser makes the id once and reuses it on retry, `preview` (required) is a digest of the packet it showed, built by the same `repairPacket` with a fixed id, and `version` (required) is the draft version it showed:

1. Read the host again and recompute the effective constraints. If they differ from the draft's basis, answer 409 with the differences and send nothing.
2. If any draft issue is unresolved, or a conflict affects a subject the draft mentions, answer 409. On a first send, if the stored draft is not at `version`, answer 409 `draft_moved` (checked before `already_sent`); if the packet built from the stored draft and the records now has a different digest than `preview` (a rule, a hold, a quoted message or the text changed), answer 409 `preview_changed` (checked once the session reports Claude Code and a transcript, so those reasons come first). On these and on `draft_changed`, the view keeps Send off while it takes up the stored draft, unless you edited it meanwhile, and says the saved version is shown only when its version changed. Both sides build the packet with one `packetOf`.
3. Check the target, on the host and inside the same script that pastes:
   - the pane id is exact (`%N`) and belongs to the session
   - the pane's foreground command is `claude`
   - the pane's registry entry says `idle`
   - the registry session id equals the draft's target

   Otherwise refuse with the specific reason: busy, waiting on a dialog, a different conversation, or gone. An empty or unmatched target always refuses. A new conversation in the same pane is never treated as the original.
4. If the transcript already holds a user record containing `[devbox repair <requestId>]`, mark it delivered and don't paste again.
5. Freeze the packet below in the store. Refuse if the session's prompt already holds text. Paste with `tmux load-buffer` and `paste-buffer -p -d` to the exact pane. Press Enter only if the pane is still the target, its prompt shows nothing but Claude Code's `[Pasted text #N +M lines]` placeholder, and the registry still says `idle` for the same session id. Otherwise leave the paste in the prompt and report it as held, with the reason, so the user can send or clear it in the terminal.
6. Track the receipt from the transcript:

   | State | Evidence |
   | --- | --- |
   | sending | the server started the send |
   | delivered | a user record containing the request id, with its uuid |
   | working | the registry says the conversation it went to is busy, or agent records follow; the receipt says "Delivered · no reply yet", since that is all Devbox knows |
   | replied | a `turn_duration` record after delivery; the reply is that turn's last agent text |
   | held | the paste is in the prompt but Enter was held back; it counts as sent, so the same draft can't go out a second time |
   | failed | the host script refused or tmux reported an error |
   | unknown | 30 s with no user record, or ssh failed after the paste began |

   Every state but replied keeps following the transcript, so a held paste the user submits from the terminal, or a late record after unknown, still lands on its own request. A retry first looks for the request id in the transcript.

   Return reads of the host run one at a time, so each appended part of a transcript is read from the version the last read left and lands once. Only the visible Return view polls, so this rarely waits. The server's own checks of the pane, the registry and the conversation follow the same rule. A held or unknown retry is checked against the conversation the first send went to. A repair belongs to a conversation, not a pane. A draft that names no conversation (it was started while the host reported none) can't be sent until the user picks the one running now. The Return read asks the host for the conversation of the open repair of the current draft, or of the draft itself, and for its pane: that pane while it still runs the conversation, otherwise any pane that does. Evidence, receipts and checks follow that conversation. A held paste sits in its own pane's prompt, so its retry goes back there while that pane runs the conversation; once no pane holds it, the paste is gone with its process, and a retry goes where the conversation runs now. A send that times out while Devbox can't see its conversation stays retryable. If the conversation is no longer running, the send becomes unknown, not failed, because it may have been submitted; the receipt says why, and the draft can't go out again until it is edited. A delivered repair whose conversation stopped says it can't see the reply. While Claude Code isn't in front, a retry is refused and the repair stays as it was. A failed send never reached a prompt, so trying it again rebuilds the packet from the draft as it is now and goes to the conversation the draft targets now. A held or unknown send may already sit in a prompt, so trying it again reuses its packet, and is refused if what holds changed since it was first sent. Trying a held or unknown send again, when the host refuses because the prompt holds text, the agent is busy or waiting, or the registry or prompt can't be read for a moment, marks it held: the paste may still be in the prompt.

The feasibility check on a throwaway session observed the user record 0.6 s after Enter and the turn end 9.5 s later, in the same transcript file, because resuming keeps the session id. Claude Code's "trust this folder" dialog accepts keystrokes too. That is why step 3 requires the registry's `idle`, not a prompt seen on screen.

### Investigation in a read-only copy

"Ask the agent to explain first" opens the question filled in with: "Using the recorded messages, explain the current failure and the limits in force. Separate what I decided from what is unknown. Don't change code or run tests." The user can edit it before sending.

`POST /api/return/ask { session, inquiryId, question }` starts the probe's ask mode on the host, detached, writing to `~/.cache/devbox/inquiries/<id>.jsonl`. It runs, in the session's folder:

```
claude -p --resume <session id> --fork-session --no-session-persistence --safe-mode --restricted \
  --tools Read,Grep,Glob --strict-mcp-config --settings <auth-only settings> \
  --permission-mode dontAsk --output-format stream-json --verbose --max-budget-usd 3 < /dev/null
```

- **Auth-only settings:** generated at each run with mode 600 from `~/.claude/settings.json`. They keep only the sign-in and model keys (`awsAuthRefresh`, `awsCredentialExport`, `model`, `modelOverrides`, `availableModels`, `enforceAvailableModels`, `fallbackModel`) and an allowlist of `env` names: the Bedrock switch, region, profile, and model names. Permissions, hooks, plugins, and plugin folders are left out.
- **Verified restriction:** the run's `init` event must list only Read, Grep, and Glob and no MCP servers. Otherwise the script kills the run, and the question fails with "Devbox couldn't make the copy read-only". Every tool call in the stream is recorded with the answer.
- **States:** draft, sending, running, replied, failed, unknown. A run with no result after 180 s is unknown. A result arriving later still attaches to its own question.
- **Labeling:** the answer opens with "**An answer, not verified** · a read-only copy of this conversation wrote it (Read, Grep, Glob), and nothing was run to check it. The original session didn't see this question.", above its text; a part the answer doesn't seem to cover is a quiet line under it, and parts that only ask for a format ("Facts vs guesses, please", "be brief", "point to the message or file") aren't checked. It shows the run's cost from `total_cost_usd`. An answer that is word for word another question's answer says so, where the answer misses part of its question or the other answer's question had nothing missed. Older answers fold under "Show the answer · not verified", and keep their notes inside. A question you wrote but didn't send is kept for the tab's life and puts the work under Not sent yet as "Question not sent".

The feasibility checks found two ways the copy was not read-only until they were closed:

- Passing the user's full settings back carried in plugin folders, whose MCP tools include one that cancels code reviews.
- `--restricted` alone drops the sign-in settings, so the run fails after minutes of retries.

Both are covered by tests of the settings builder.

### Showing saved records

**Show saved records about this** searches the work's records for the question's words and shows the matching records, each cut at 400 characters. It says which of the question's words records mention and which none do ("Records that mention “backoff”. No saved record mentions “jittered”. The question isn't answered or verified."). It never changes a pending question's state.

## Stage 1d: independent states

- **Separate identities:** each question and repair has its own id, text, time, target, channel, and evidence version. Users never see or manage the ids.
- **Unsent work:** a new question is "not sent", and it never inherits an older question's receipt. Asking a new question, or showing saved records, leaves an older running question untouched.
- **Binding replies:** a reply attaches to the request it answers. A fork's output carries its question's id, and a repair's reply follows its own user record. Replies to an earlier evidence version say which version they used.
- **The overview card:** it shows the one next relevant state: "Draft not sent", "Question answered", "Repair replied, review it", "Delivery unknown", or "Repair waiting in the prompt". "Repair replied, review it" stays until you accept the reply or send a follow-up; an unsent follow-up shows as "also: Draft not sent". The card learns of a reply when the Return view or a brief reads the host; a brief is read again when the session's activity changes, so the card follows within a poll. After you accept, it says "Result accepted · merge is still yours", or "Accepted · 2 things it may have missed" while the reply left lines of the request unmentioned. So does a delivered repair whose conversation stopped; its receipt says Devbox can't see the reply. Ordinary waiting appears as "Waiting on agent" in the quiet lane, never under Needs you, and blocks nothing unrelated; its row says what it waits for, "Waiting for the reply to the repair you sent. It comes back under Needs you, so you can leave.", instead of the agent's last message, and "You sent “…”" with the line that sums the repair up (the summary's `sent`: its Decision line, else its first line with two words the quoted limits don't carry) instead of an older decision. A running question is listed there too, as "Question running", with "Waiting for the answer to your read-only question. It comes back under New since you looked, so you can leave." The state and the action come from one ordered list (reply, unknown or held send, then an agent waiting on you, then a failed check, then answer, pending repair, running question, unsent draft, unsent question, accepted), so the badge and the button never disagree, and the row's other states follow the badge ("also: Check failed · Draft not sent"). Agent words on a row are quoted, and a reply carries "the reply's word, not a check". The Now tab's count, the page's Needs you and the session sidebar's Needs you count the same works. The server follows a running question itself: a summary that finds one starts a check 15 s later, so the overview learns of the answer without the work page open, and the summary never waits on the host. A reply's `[devbox result id]` tag is left out of the home row. On the home list, a session goes under Needs you when its lane says so, a reply or an unknown or held send waits for you, or the work's brief shows a check that failed in any session of the work after the newest repair that went out and after your visit before this one ended (so it stays while this visit lasts, whether or not you act on it, and leaves Needs you once that visit ends, after 30 minutes without looking at the work, since only failures are recorded and Devbox can't see it pass); under Waiting on the agent while a sent repair is sending, delivered or being worked on, or a question runs; under New since you looked when an answer arrived (ahead of Waiting on the agent, so an arrived answer is never listed as waiting) or it changed; under Not sent yet when all that's left is your own unsent draft or question; and under "Accepted · merging is yours", with a check icon, when all that's left is a result you accepted, so the merge stays in view after the visit ends ("You can leave now" then adds "Merging what you accepted is still yours."). A row's failure reads "Latest" instead of "Since you left" once you have looked since it failed. The work page's rail shows each work's status as Now does, the open one with the page's live status. A row whose status is "Check failed" has the failed check's icon. A reply's card names how many asks the reply leaves out ("Repair replied · 2 things it may have missed"), counted like the result step: each line you asked, then each message you attached once.
- **Accept result:** this binds to the repair's request id, its reply uuid, and the evidence version at sending. If a constraint changed after sending, acceptance is disabled, with the change shown. Acceptance records a decision only. It never merges, pushes, or closes anything.

## Prompt contracts

These are the exact texts Devbox sends. `recover.ts` builds them and tests pin them.

### Repair packet

```
[devbox repair {requestId}]
Purpose: repair. Make the changes below in {cwd}. You may run the tests needed to check them. Do not merge, push, or deploy.
Target: this session, {session}.

{draft text, each line kept as an earlier comparison ending " (Earlier comparison only, not a requirement.)"}

What this is based on, quoted from this conversation:
- Holds now ({who}, {time}): "{sentence}"{ Replaces "{old sentence}" ({who}, {old time}).} Reason: {reason}.|No reason recorded.{ The replaced limit's reason may not apply to this one.}
- Decided for this work (you, now): {value}, between "{a}" ({time a}) and "{b}" ({time b}).
- Latest recorded failure ({this session|session}, {time}): "{first two lines, joined by ' · '}". Evidence to check, not my review or acceptance of the changes. (When the failure is no newer than the last repair Devbox sent, the line starts "Recorded failure from before the last repair".)
- Rule ({who}, {time}): "{sentence}"
If the request above conflicts with one of these rules, stop and ask me before acting on it.
I set aside my rule{ in {session}} from {time} for this request only: "{sentence}"
For this request only, I make an exception to my rule{ in {session}} from {time}: "{sentence}", for this line only: "{line}". The rest of the rule still holds.
Agent messages from the other sessions in this work, quoted as written and not checked:
- {session} ({time}): "{message}"

When you finish, start your reply with "[devbox result {requestId}]", then list what you changed and which tests you ran.
```

The precedence line appears only when rules are quoted. Rules are never gated like limits, so a rule such as "Don't edit anything yet" can be older than the request that ends it. The target session's rules are quoted unless unticked; another session's only when ticked. When a limit has no reason but the one it replaces had one, the packet says that reason may not apply. The other sessions' messages appear only when the draft keeps them.

`{who}` is "you" for this session's messages and "you in {session}" for another session in the same work. When any quoted line comes from another session, the heading reads "quoted from this conversation and the other sessions named below:".

### Investigation prompt

```
[devbox question {inquiryId}]
Read-only investigation. You are a read-only copy of this conversation with only Read, Grep and Glob. The original session will not see this question or your answer.
Answer from this conversation and the files under {cwd}. Use three headings: Facts (each with the message time or file it comes from), Inference, Unknown. If the records don't answer the question, say so under Unknown. Do not say you ran or changed anything.

Question: {question}
```

The investigation's restriction comes from the CLI flags, never from this prompt. The prompt only shapes the answer.

## Safety invariants

Each invariant is a named test.

1. Nothing is pasted unless the target is an exact pane id that belongs to the session, has `claude` in front, is idle in the registry, has the draft's session id, and has an empty prompt. Enter is pressed only when the prompt shows just the paste and the agent is still idle.
2. An empty, malformed, or mismatched target refuses before any tmux write.
3. A retry never pastes twice: a request id found in the transcript means delivered.
4. A repair whose evidence changed after its last check is refused, and the draft is kept.
5. An unresolved draft issue, or a conflict on a subject the draft mentions, blocks repair only. Reading, editing, saving, and questions stay available.
6. A question never reaches the original session. A copy whose `init` lists any tool beyond Read, Grep, and Glob, or any MCP server, is killed before it answers.
7. A new question never inherits an older receipt. Showing records never changes another question's state.
8. Acceptance is refused for a result produced under constraints that have since changed.
9. A model never writes any text Devbox shows, except a question's answer, which is labeled as coming from the copy.

## User testing with fresh agents

### Scenarios

A setup script on the host builds each scenario in its own folder, a local git repository with no remote, and its own throwaway tmux session named `devbox-scn-<n>`. Transcripts are created by real Claude Code prompts, then their timestamps are moved back two to three days so "away" is real to the dashboard.

| ID | Scenario | Ground truth |
| --- | --- | --- |
| S1 | Retry limit changed from 2 to 1 with "instead of"; the saved draft still says 2 | effective limit 1 with its source; the draft line needs a change or an earlier-comparison note; the repair goes to `devbox-scn-1` |
| S2 | An older question is still running; the user asks a new one and looks up records | the old question stays running and gets its own answer; the new one is separate; the record lookup claims no answer |
| S3 | The first send fails because the agent is busy; a retry after it goes idle | refusal names the reason; the retry delivers exactly once |
| S4 | A shell session on another repository shares the folder name; a second Claude session shares the branch | the shell session isn't grouped; the branch session is, with its reason; separating and undoing work |

The ground truth for each scenario and a strong handoff document (goal, stopping point, constraints with reasons, next step, evidence links) are written and committed before any evaluator runs. Changing either afterward starts a new round.

### Evaluators

Each round uses 3 fresh agents that have never seen this design. Each one plays a developer returning after two days, and does each scenario twice:

- once with the handoff document and a terminal attached to the session
- once with Devbox

The order alternates between evaluators. The prompts call the two conditions "notes" and "dashboard", and evaluators aren't told which one is being built. They drive Chrome through a small command tool (`snapshot`, `click`, `type`, `screenshot`), never the API.

Each run is scored from the evaluator's written answers and the actual transcripts:

- the effective constraint and the stopping point, each with its source
- the action sent, its scope, and its target
- critical violations: wrong target, an unauthorized write or test, a stale instruction sent, a duplicate send, or accepting a result made under old constraints

A round passes when all 12 Devbox runs are correct with 0 critical violations, and at least 2 of 3 evaluators prefer the dashboard to the notes when asked after both conditions. Fixes go into the next round with new evaluators. After 4 rounds without a pass, work stops and the results are reported as they are.

### Cost

Each Claude Code turn on this account cost about $1 in the checks. Building the scenarios takes about 20 turns. A round takes about 12 repairs plus 6 questions, so about $20 per round and about $100 for four rounds. Every turn is in throwaway folders and sessions.

## Limits of this release

- Only Claude Code sessions in tmux. Codex sessions are listed, but not recovered.
- Constraint reading is limited to the rules above. A sentence outside them shows as a decision without a constraint label, and the UI says Devbox might have missed constraints worded differently.
- There is no remote cancellation. Stopping tracking a question changes only what the dashboard shows.
- Drafts and corrections stay on this laptop.
- Agent-based testing can show that the workflow is correct and usable. It cannot show human time savings or willingness to pay, which the PRFAQ's trial is for.
